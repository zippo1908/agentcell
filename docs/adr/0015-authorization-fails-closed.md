# ADR-0015: 控制面读不到账号库时,授权关门

Status: accepted
Amends: [ADR-0013](0013-authorization.md)(它只写了「谁能做什么」,没写「读不到的时候怎么办」)

## Context

平台作用域的授权此前散在两处 `if p.Admin`,收口到 `canPlatform` 时,
我把原来那句「数据库读不到就按会话 cookie 里的声明放行」原样保留了下来,
理由是「保持行为不变」。

这个理由是错的,而且错得比它看起来严重。收口之后 `grantsOf` 在出错时返回的
状态是「这个身份没有账号行」——而「没有账号行」在建项目那条规则里是**放行**
(它是为 OIDC 和静态令牌这类先于该授权存在的身份准备的兼容规则)。于是:

    数据库抖一下  →  没读到  →  被当成「没有账号行」  →  放行建项目

**一次存储故障会给所有人发权限。** 这不需要对手,只需要磁盘满一次。

会话 cookie 上的 `Admin` 声明也不能当兜底。它是登录那一刻写进去的,而
「他现在还是不是管理员」正是此刻唯一读不到的那件事——拿一个无法核验的声明
去替代核验,等于把「暂时不可用」变成「暂时不设防」。

## Decision

**控制面不可用可以让工作停下,但不能让权限变宽。**

`standing` 把三件以前混在一起的事分开:

| 状态 | 含义 | 判定 |
|---|---|---|
| `standingNoRow` | 这个身份**没有**账号行(OIDC、静态令牌) | 兼容规则,建项目放行 |
| `standingDeleted` | 账号行**曾经有、已被删** | 拒绝,理由是「账号不存在」 |
| `standingUnavailable` | 账号库**读不到** | **拒绝**,理由说明这是有意的 |
| `standingNoAccountSystem` | 这个部署压根没有账号体系 | 放行——这是配置,不是故障 |
| `standingBootstrap` | 部署令牌 | 放行,见下 |

**「没有」和「读不到」的区别就是这条 ADR 的全部内容。** 前者是关于部署的
一个事实,后者是一次故障;把故障当事实处理,是 fail-open 的标准形状。

**故障期间管理员也一并拒绝。** 「出故障时放管理员过去」是那个诱人的例外,
而它是自毁的:管理员身份恰恰是此刻无法核验的那个声明,所以这个例外对任何
声称自己是管理员的人同样开放。

### 逃生通道只有一条,而且是设计出来的

fail-closed 只有在「还有东西能用」时才可行,否则它就是在事故现场把运维也
锁在门外。这里那个东西是**部署令牌**:它在查库**之前**被解析,所以库挂了
它照常工作——而库挂了正是有人需要它的时候。

这条通道是唯一的,窄的,而且有测试盯着
(`TestTheBreakGlassPathSurvivesAnOutage`)。它失败意味着 fail-closed 已经
退化成一把锁死自己的锁。

## Consequences

**账号库现在是平台级操作的硬依赖。** 它挂了,建项目和邀请都会停——这是有意
选择的结果,不是退化。日常操作(开终端、派活、看预览)不经过这条路,不受影响。

**判定带上了 `Rule` 和 `Reason`。** 「为什么停了」在故障期间是最需要被答出来
的问题,而一个返回 `bool` 的函数答不了。运维看到的是「账号库暂时读不到,平台级
操作已停用;这是有意的」,而不是一个没有解释的 403。

**Cell 作用域尚未享有这一条。** `can()` 仍返回 `bool`,而且它读的是 Cell 对象
(来自 API server 缓存)而不是账号库,故障形状不同。把 `Decision` 推到 Cell 作用域
是下一步,不在这条 ADR 里。

**这条排在 egress 收紧和 Principal ID 解耦之前。** 后两者需要一个对手才会
造成损失;这一条只需要一次磁盘写满。
